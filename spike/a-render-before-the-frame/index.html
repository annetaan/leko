Does a render beat the next frame?

A handler that calls setState and then leko.reached() leaves the framework's render behind it, and Leko requests a frame to draw the next step in. This page asks, for four kinds of work a call can leave behind, whether that work runs before the frame requested after it, between that frame and the one after, or later still.

Each trial starts in a timer task, the way code after await save() does, at a random point of the frame: a setTimeout of 0–16ms set from a requestAnimationFrame callback. Inside that task it leaves one variant's work behind and then calls requestAnimationFrame; that callback, frame 1, requests frame 2. The trial records where the work's own mark landed.

  • microtask — queueMicrotask. React inside its own handlers, Vue, Svelte, Preact and Lit flush this way. The specification runs it before any frame; this row is the page checking itself.
  • message-in-call — a MessageChannel message posted inside the call, the way React 18's Scheduler posts a render outside React's own handlers.
  • message-from-microtask — a microtask queued in the call that posts the message, the way React 19 schedules a render outside its own handlers (processRootScheduleInMicrotask → scheduleCallback).
  • timeout-0 — setTimeout(0), for comparison only.

Two loads: idle, and busy, where a requestAnimationFrame loop spins the main thread for about 12ms every frame for the whole batch. A red cell is a trial that lands after frame 1 for a message-* variant, or anywhere but before frame 1 for microtask. timeout-0 is never judged. node run.mjs reads the same window.spikeFrame.measure() in more than one engine.
